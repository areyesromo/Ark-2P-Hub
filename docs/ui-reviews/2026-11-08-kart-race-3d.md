# Kart Race 3D UI review

Reviewed: 2026-11-08. Scope: Kart Race 3D TV interface and phone controller.

This is a source review. The game, WebGL renderer, Blender and ComfyUI jobs were not started. Recommendations about readability and screen space still require visual checks on a TV, desktop and phone. No game code was changed for this review.

## Main finding

The 3D game wraps the existing Kart Race TV interface and directly reuses its phone controller. The shared setup, start lights, readiness, input preferences and results provide a useful foundation. The presentation is still designed around a single top-down play area, while the 3D game has two chase-camera views.

## Recommended priorities

| Priority | Change | Reason and proposed behavior |
| --- | --- | --- |
| 1 | A HUD for each viewport | Put player identity, position and lap at the top of each player's half. Keep the active item and drift charge clearly visible near its lower edge. Make coins, speed and lap timing secondary. Keep the center of both driving views clear. |
| 1 | Separate alerts from lap information | The current lap line can be replaced by reaction time, jump-start or shortcut messages. Preserve lap progress and show short alerts in a separate area. Avoid adding overlapping banners. |
| 1 | Visible loading and recovery | Show an indeterminate loading message while the 3D scripts and scene initialize. Distinguish unsupported graphics from a loading failure where detectable. Provide retry and a clear route back to the lobby using the existing controller/phone interaction model. Do not invent a percentage without measurable progress. |
| 2 | More visual race setup | Use the title “Kart Race 3D”; enlarge the track preview and the two player selection cards. Separate track/rules from each player's character and tyres. Keep each player's ready state visible and explain exactly whose confirmation is still needed. |
| 2 | Course navigation | Add a compact map with two labeled player markers, the finish line and direction of travel. This becomes more valuable for the planned large canyon tracks. Do not imply a route is playable just because concept art exists. |
| 2 | Contextual control prompts | Show the few actions relevant to setup, racing or results, using the selected input method. The current controller help combines driving, setup, between-race and end-of-match commands in one long string. |
| 2 | Clearer race results | Lead with winner, finishing order and times when available, followed by cup progress when relevant. Make rematch/settings/lobby choices and each player's readiness easy to scan. TV prompts must work through the phone and gamepad, not depend on mouse clicks. |
| 3 | Refine the phone race screen | Preserve all four steering methods, saved preferences, landscape/portrait support and existing release handling. Emphasize gas, brake, drift and the current item. Make the empty item state quiet and drift readiness legible without relying on color alone. |
| 3 | Display and comfort options | Evaluate horizontal versus vertical split after the HUD is proven. Offer reduced boost camera FOV movement and readable HUD scaling. Split orientation needs coordinated viewport, camera aspect and overlay changes; it is not just a CSS option. |

## Suggested first pass

1. Give the shared TV factory an explicit, opt-in 3D presentation option and title.
2. Add a compact, labeled HUD for each player, with persistent lap progress and separate transient alerts.
3. Add loading and failure states in the 3D stage wrapper.
4. Rework 3D setup spacing and context-specific prompts.
5. Validate these changes before adding the minimap, phone refinements or split-layout settings.

Use the existing player colors with P1/P2 text, strong contrast and solid or translucent HUD backgrounds. Avoid text over an unprotected moving scene. Use brief transitions and avoid perpetual flashing for routine states.

## Keep the scope isolated

- The 3D host already calls `ArkKartTV.make({ stage })`; extend this factory with opt-in presentation options rather than changing the default layout for every game.
- Scope TV styles beneath `.kr-host.kr-3d` and keep the original Kart Race defaults.
- The 3D phone currently aliases the 2D renderer directly. Introduce an opt-in factory or separate 3D wrapper before changing its layout, so the 2D phone experience remains unchanged.
- Keep existing race rules, physics, readiness checks and input behavior intact. These recommendations concern presentation and navigation.
- Reuse lightweight track geometry for a map. Do not add another 3D render pass solely for the minimap.

## Validation for implementation

Once the user is finished gaming, inspect setup, loading/failure, countdown, racing, battle, standings and final results. Include long player names, empty/full item queues, warnings, both ready states and cup progress. Check TV-distance readability, smaller desktop sizes and phone portrait/landscape. Verify both players' identity and HUD alignment, input-method switching, safe touch release and navigation using only a gamepad or phone. Confirm the original 2D game has no layout or behavior changes. Check rendering performance only when local GPU use is authorized.
